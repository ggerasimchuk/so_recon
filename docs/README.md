# SO-RECON — действующий комплект требований 4.0

**Дата:** 13 сентября 2026 г. Комплект развивает существующий проект после E00. Готовое основание, данные, окружение и история запусков сохраняются; следующий план — E01.

## Документы и приоритет

1. [SPEC.md](SPEC.md) — единая нормативная архитектура: таргет, физика, ML, вероятностная коррекция, научные критерии и матрица верификации.
2. [STAGES.md](STAGES.md) — последовательность E00–E14, зависимости, границы этапов, приёмка и образец запроса на план E01.
3. [COMPUTE_PROFILES.md](COMPUTE_PROFILES.md) — стартовые размеры экспериментов, RAM/disk/wall limits, измерение полной стоимости и возобновление.
4. [DECISIONS.md](DECISIONS.md) — принятые изменения 3.0 → 4.0, сохранение E00 и точные задачи совместимости для начала E01.
5. [SOURCES.md](SOURCES.md) — первоисточники методов/API, статус их проверки и граница проектных численных решений.
6. [DATA_AUDIT.md](DATA_AUDIT.md) — сохранённые фактические сведения о CSV и ограничения; воспроизводимый ETL-аудит — E04.
7. [RESEARCH.md](RESEARCH.md) — литературный синтез прежней архитектуры; выбор текущих компонентов определяется SPEC/DECISIONS.

Подтверждённая семантика исходных данных имеет приоритет над ошибочной формулировкой документа. Научные требования задаёт SPEC; последовательность — STAGES; ресурсные настройки — COMPUTE_PROFILES. План этапа не меняет target/likelihood/physics/validation ради удобства реализации. Новые научные изменения оформляются ADR до закрытой проверки.

## Текущая архитектура

```text
conditional geological prior + controls/completions
    → JutulDarcy physical histories and hidden So
    → graph-temporal conditional NSF proposal
    → defensive SMC correction with full physical likelihood
    → weighted physical states, uncertainty and supported report zones
    → paired engineering scenarios
```

ML предлагает распределение физических параметров; окончательные состояния получает симулятор. Его польза проверяется при одинаковой разрешённой информации и зарегистрированном бюджете. Основная state metric — MAE; отдельные критерии обязательны для локализации зон, нефтяного инвентаря и полевого контроля.

Малая synthetic-физика появляется в E01, inverse reference — E02, первый полный ML+SMC опыт — E03. Реальные данные канонизируются в E04, полевой pilot/timeline определяется в E05, физика — E06, полеподобный полный опыт — E07. Последующие E08–E14 дают основной corpus, научное сравнение, полевую реконструкцию и инженерные продукты.

## Сохранение E00

[Исторический отчёт E00](../reports/stages/E00.md), [его план](superpowers/plans/2026-09-13-e00-foundation.md), frozen smoke и manifests сохраняют версию **3.0**. Текущий runtime/config также ещё 3.0. Новая документация 4.0 не утверждает, что исполнитель уже поддерживает новые contracts.

**Первый блок нового E01:** совместимость version/config/lineage, минимальные CaseBundle/ForwardResult, persistent Julia worker и ресурсные guards. Density/SMC contracts вводятся в E02, ML — E03. Создавать E00 заново или переносить `julia/`/сырьё в новую структуру не требуется.

## Как писать следующие планы

Прочитать корневой README, этот файл, SPEC, STAGES, COMPUTE_PROFILES и DECISIONS; затем тематические разделы DATA_AUDIT/SOURCES/RESEARCH и фактический код. При наличии локального AGENTS.md также соблюдать его инструкции. Новый план хранится в `docs/superpowers/plans/`, указывает `spec_version=4.0`, полный заголовок этапа, требования SPEC, входные gates, артефакты, проверки и ресурсный бюджет.

Присланные корневые `SPEC_v2.md`, `STAGES_v2.md`, `COMPUTE_PROFILES_v2.md` — варианты для обсуждения. Они не задают параллельные требования. Старые номера этапов нельзя переносить без таблицы соответствия в STAGES. Следующий запрос приведён в STAGES §7 и начинается с **плана E01**, а не повторного E00.
