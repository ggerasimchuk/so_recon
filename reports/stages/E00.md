## 6. Ограничения

1. CI не настроен (нет remote; precompile JutulDarcy в CI дорог). Роль чистой установки
   выполняют `make gate` и `make gate-clean`.
2. Julia-smoke — проверка работоспособности окружения, не верификация физики (E05).
3. `physical_line_count` — физический счёт строк; переводы строк внутри закавыченных полей
   не учитываются, потому что E00 не парсит CSV. Реальное число записей определяется в E01.
4. Случаев без run-записи два, и оба — **до** того, как прогон вообще может начаться:
   (а) argparse отверг командную строку (`so-recon nope`, `--help`, отсутствующая
   подкоманда) — выход происходит через `SystemExit` внутри `parse_args`, когда `main`
   ещё не знает ни root'а, ни конфигурации; (б) repository root не найден — писать некуда.
   Всё, что происходит после этих двух точек, записывается: конфигурационная ошибка,
   отсутствующая Julia, произвольное исключение в теле прогона. Границей остаётся
   `RunRecordUnavailableError` — непригодное дерево артефактов, где запись нельзя ни
   открыть, ни закрыть.
5. GNU Make 3.81 не поддерживает `.SHELLFLAGS`, поэтому `pipefail` реализован в
   `scripts/gate.sh`.
6. Расхождение документации: `STAGES.md` (строка 671) ссылается на
   `docs/README_SO_RECON.md`; фактический файл — `docs/README.md`.
7. **Каталог `.idea/` отслеживается git, хотя `.gitignore` (строка 24) содержит `/.idea/`.**
   Шесть файлов (`.idea/.gitignore`, `.idea/modules.xml`, `.idea/so_field.iml`,
   `.idea/vcs.xml`, `.idea/inspectionProfiles/*`) попали в первый коммит, а `.gitignore`
   не действует на уже отслеживаемые пути. IDE постоянно переписывает `.idea/so_field.iml`,
   поэтому рабочее дерево всегда «грязное» — **именно поэтому каждая run-запись этапа несёт
   заметку `working tree was dirty at run start` и `git_dirty: true`**. На корректность
   детерминированных артефактов это не влияет (проверка детерминизма в `gate.sh` смотрит
   только на свой список путей). Однострочное исправление —
   `git rm -r --cached .idea` с последующим коммитом — оставлено владельцу репозитория:
   это решение о составе версионируемых файлов, вне рамок E00.
8. **Снято в финальной волне правок (было ограничением, стало исправлением).** Ранее
   `reports/environment_report.md` и `reports/manifests/environment.json` коммитились
   вместе с полями-отпечатками машины (`os`, `arch`, `uv_version`,
   `julia_executable_version`), и это принималось как «детерминизм в пределах одной
   машины». Цена была реальной: у коллеги на Linux/x86 шаги 1–7 `make gate` проходят, а
   шаг 8 печатает `gate FAIL: tracked deterministic artifacts changed` — ложный сигнал
   дрейфа, произведённый собственным gate'ом ветки, ровно против поправки 10 («чтобы

  `case.json` → результат с `input_sha256`.
- **E05, ограничение SPEC 19.15 (передаётся явно).** `_failure_detail` в
  `src/so_recon/simulator/julia_bridge.py` при падении Julia берёт её собственное поле
  `message` из `--out` и кладёт этот текст в заметки `run.json` (усечённым до 4000
  символов). Для синтетических smoke-кейсов это безвредно — в сообщении нет ничего, кроме
  формы самого кейса. Но как только через мост пойдут реальные данные месторождения,
  интерполированное значение в сообщении Julia (имя скважины, координата, значение ячейки)
  окажется в run-записи, а run-записи — это lineage, который живёт дольше и ходит дальше,
  чем сами данные. **E05 обязан это учитывать:** либо санировать `message` перед записью,
  либо фиксировать только структурный код ошибки, оставляя подробности в `run.log` внутри
  run-каталога.
- **Все этапы:** правило «один запуск = один `run_id` + `run.json` +
  `resolved_config.json` + `run.log`», immutable `ArtifactRef` и разделение
  детерминированных коммитируемых артефактов и run-штампов.
